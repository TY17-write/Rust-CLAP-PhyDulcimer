# 既知の問題・制約

本プロジェクトの問題を1箇所に集約する。**問題を見つけたらその場で追記する** (後回しにしない)。

リアルタイム制約ゆえに**意図的に諦めた近似**も「仕様上の制約」として記録する。
これが設計判断の記録になり、後から「なぜこうなっているのか」を追える。
**やらなかった判断こそ記録に値する。**

## 記入書式

```markdown
## [D-000] 一行で分かる表題
- 発生フェーズ: Phase N
- 分類: 音質 / 性能 / 検証手法 / 移植性 / 仕様上の制約 / 未解決
- 状態: 未対応 / 回避策あり / 恒久 / 修正済み (コミットへのリンク)
- 症状: 観測される事実
- 原因: 分かっていれば。**分からなければ「未特定」と書く**
- 回避策 / 対応方針:
- 参照: 論文・コミット・計画の該当節
```

## [D-001] 部分音の T60 は 0.4 秒より短いと測れない

- **発生フェーズ**: Phase 0
- **分類**: 検証手法
- **状態**: **未対応** (Phase 1 で必要になったら直す)
- **症状**: `analyze --partial-t60` が短い減衰に対して `—` を返す。単一の減衰正弦波
  (1000 Hz) で T60 を振って測った境界:

  | 設計 T60 | 測定 | R² |
  |---|---|---|
  | 1.000 s | **1.000** | 1.0000 |
  | 0.600 s | **0.600** | 1.0000 |
  | 0.500 s | **0.500** | 1.0000 |
  | 0.375 s | — | — |
  | 0.250 s | — | — |

  **0.5 秒までは正確、0.375 秒から測れない。**
- **原因**: [`estimate_partial_t60`] は窓 200 ms / ホップ 50 ms が固定で、
  `fit_t60` は「ピークから −5 dB 落ちた点」から「−20 dB 落ちた点」までに直線を
  当てる。この 15 dB ぶんの時間は `T60/4` なので、T60 = 0.375 s なら 0.094 s =
  ホップ 2 個ぶんしかなく、`end <= start + 2` の条件で棄却される。
- **対応 (Phase 3)**: [`estimate_partial_t60_with`] で窓とホップを引数にした。
  CLI は `--t60-window` / `--t60-hop`。目安は **ホップ ≤ T60/12**。
  検証: T60 = 0.375 / 0.25 / 0.15 s がすべて誤差 10% 以内で測れることを
  テストで固定 (`short_t60_is_measurable_with_a_narrow_window`)。既定 (0.2/0.05)
  では従来どおり測れないことも同じテストで固定してある — **既定の沈黙は仕様**で、
  短い減衰を測るときは明示的に狭めること。
- **参照**: `tools/analyze/src/lib.rs` の `estimate_partial_t60_with` / `fit_t60`

## [D-002] 部分音が混在すると測れる T60 の下限が上がる

- **発生フェーズ**: Phase 0
- **分類**: 検証手法
- **状態**: **原因未特定**
- **症状**: 8 本の部分音を重ねた信号 (f0 = 220 Hz、`--t60 3.0 --t60-taper 1.0`、
  第 n 部分音の設計 T60 = 3.0/n) を測ると、n = 5 / 7 / 8 だけ `—` になる。

  | n | 設計 T60 | 測定 |
  |---|---|---|
  | 1 | 3.000 | **3.000** |
  | 2 | 1.500 | **1.500** |
  | 3 | 1.000 | **1.000** |
  | 4 | 0.750 | **0.750** |
  | 5 | 0.600 | — |
  | 6 | 0.500 | **0.500** |
  | 7 | 0.429 | — |
  | 8 | 0.375 | — |

  n = 7 / 8 は [D-001](#d-001-部分音の-t60-は-04-秒より短いと測れない) で説明が付く。
  **説明が付かないのは n = 5 (0.600 s) が落ちて n = 6 (0.500 s) が通ること。**
  単独の正弦波なら 0.600 s も 0.500 s も測れている (D-001 の表)。
- **原因 (Phase 3 で特定)**: **D-001 と同根のホップ量子化。** 当初の仮説 2 つ
  (隣接部分音の漏れ込み / 走査周波数のずれ) は**両方外れ**。当てはめ区間
  (−5 dB → −20 dB = T60/4) がホップ 50 ms で 3 点前後しか取れない境界では、
  ピークの位置がホップ格子のどこに乗るかで点数が 1 個増減し、`end <= start + 2`
  の棄却をまたぐ。n = 5 と n = 6 の違いは境界上の偶然だった。
- **検証**: 同じ WAV を `--t60-hop 0.02` で測り直すと、**8 本全部が設計値どおり
  (0.600 / 0.429 / 0.375 s、R² = 1.0000) に出た。** 混在による劣化は無い。
- **教訓**: **測定器が「測れない」と言ったとき、それを「値が無い」と読まないこと。**
  そして原因の仮説は書くだけでなく潰すこと — 2 つ書いてどちらも違った。
- **参照**: `tools/analyze/src/lib.rs`、D-001 の対応

## [D-003] WAV の書き出しが render と analyze の 2 か所にある

- **発生フェーズ**: Phase 0
- **分類**: 仕様上の制約
- **状態**: **恒久** (意図的)
- **症状**: `tools/render/src/main.rs` の `write_wav` と、`phydulcimer_analyze` の
  `write_wav` が同じことをしている (約 30 行)。
- **なぜそうしたか**: 共有すると **レンダラが解析ツールに依存する**という筋の悪い
  依存方向になる。逆に WAV I/O だけの crate を切ると、Phase 0 の時点で crate が
  1 つ増える。**30 行の重複のほうが安い。**
- **食い違ったときにどう気づくか**: `analyze` が `render` の出力を読めなくなるので、
  Phase 0 の完了条件 (`render` → `analyze` で設計値が読める) がそのまま検出器になる。
  加えて `tools/analyze/tests/roundtrip.rs` が lib 側の往復を固定している。
- **見直す条件**: プラグイン側 (Phase 2) でも WAV を書くようになったら、3 か所目に
  なる前に crate を切る。

## [D-004] --peak の既定を PhyPiano から変えた

- **発生フェーズ**: Phase 0
- **分類**: 仕様上の制約
- **状態**: **恒久** (意図的)
- **内容**: `render --peak` の既定を **0 (正規化しない)** にした。PhyPiano は 0.9。
- **理由**: PhyPiano では A/B 比較のたびに `--peak 0` を付け忘れ、**2 本のレベルが
  揃って差が消える**事故を繰り返した (引き継ぎメモに「頻出事故」として残っている)。
  既定を安全側に倒すほうが、注意力に頼るより確実。
- **副作用**: 出力が小さいまま書かれるので、そのまま聴くと音が小さい。聴くときは
  明示的に `--peak 0.9` を付ける。
- **固定方法**: `tools/render/src/main.rs` の `peak_defaults_to_no_normalisation`
  テストが 0 を固定している。**変えるならこのテストごと変えることになる。**

## [D-005] 信号全体の T60 はこの楽器では意味を持たない

- **発生フェーズ**: Phase 0
- **分類**: 検証手法
- **状態**: **恒久**
- **内容**: `analyze --t60` は信号全体の RMS 包絡に単一の指数を当てる。
  打弦楽器では部分音ごとに減衰時間が違うので、全体の包絡は
  「前半は高次部分音の速い減衰、後半は基音の遅い減衰」の 2 段になり、
  単一の指数では表せない。
- **ダルシマーではさらに悪い**: **ダンパーが無いので他の弦が共鳴して鳴り続ける。**
  1 音を鳴らしても、全体の包絡はその弦の減衰を表さない。
- **使ってよい範囲**: Phase 0 の疎通確認 (単一の減衰正弦波) まで。
  モデルが入ったら `--partial-t60` に切り替える。
- **参照**: `plan.html` の P10 (音色の追い込み)

## [D-006] 参照音源を持たない

- **発生フェーズ**: Phase 0 (計画時の決定)

  置いてある。**ここを緩めると寄る辺が無くなる。**
- **参照**: `plan.html` §10、`research.md` §5

## [D-008] SIMD は Phase 8 を待たず移植した

- **発生フェーズ**: Phase 1
- **分類**: 仕様上の制約 (計画からの逸脱)
- **状態**: **恒久**
- **内容**: 計画では「Phase 1 はスカラで正しさを確定、Phase 8 で SIMD 化」だったが、
  `modal.rs` は PhyPiano の Phase 7 で SIMD 化済み・テスト済みのものをそのまま移植した。
- **理由**: 動作実績のある実装をスカラに**書き戻す**ほうが、バグの入る余地と

  移植したテスト (極の半径と角度・低周波の音高保持・T60) が担う。
- **注意**: Phase 8 の作業は「SIMD 化」ではなく「全弦常時走行の実測とチューニング」になる。
- **参照**: `crates/phydulcimer-core/src/modal.rs` 冒頭

## [D-009] 共振器のホットループに累算器を足さない

- **発生フェーズ**: Phase 1 (PhyPiano P-027 からの継承)
- **分類**: 性能
- **状態**: **恒久** (指針として維持)
- **内容**: `ModalBank::process_sample` のループに出力以外の累算器を足すと、
  baseline (SSE2) ビルドでレジスタが尽きてスピルし、**別ループで回すより 1.4 倍遅く**なる
  (PhyPiano の実測: 融合 3.85 µs vs 別ループ 2.74 µs)。`f32x8` は AVX 無しだと
  SSE レジスタ 2 本を食う。
- **本プロジェクトでの帰結**: 縦振動用の `weighted_square_sum` は移植時に削除した
  (この楽器では縦振動を当面見送るため)。**将来ブリッジ結合 (Phase 4) で内積が
  要るときも、別ループで書くこと。**
- **参照**: `crates/phydulcimer-core/src/modal.rs` の `process_sample`

## [D-010] オーバーサンプルは 16 倍。デシメーションフィルタは不要

- **発生フェーズ**: Phase 1
- **分類**: 検証手法 / 性能
- **状態**: **測定済み** (2026-08-31)
- **測ったこと**: 接触中のオーバーサンプル倍率を 2–64 で振り、部分音レベル
  (アナライザ経由) を os=64 と比較した。

  | os | 木 (最大ずれ) | フェルト (最大ずれ) |
  |---|---|---|
  | 4 | +10 dB 以上 (全域) | 数 dB 明るすぎる |
  | 8 | **20 dB (第 10 部分音)** | 1.8 dB |
  | **16** | **≤ 1.5 dB** | **≤ 0.5 dB** |
  | 32 | ≤ 0.5 dB | ≤ 0.5 dB |

  **収束の判定は接触時間ではなくスペクトルで行った。** 木の接触はチャタリング
  ([D-012](#d-012-木の撥はチャタリングし接触時間は収束した観測量ではない)) で、
  接触時間の合計は倍率に対して収束しない (0.09 → 1.41 ms と増え続ける)。
- **決定**: 既定 16 倍。コストは接触中 (数 ms) だけなので許容。
- **デシメーションフィルタ**: **不要と判定。** drop (フィルタ無し) と average を
  比べ、部分音レベルは 0.01 dB まで一致、部分音の無い周波数のフロアは両方式とも
  **−129 dB 以下**。共振器バンクの状態は狭帯域で、ナイキスト超のエネルギーを
  そもそも持たない。PhyPiano で未測のまま残った P-011 への、この楽器での答え。
- **モード打ち切りの感度** (木・打弦点 0.05・os=16): 60 本で全数 (75 本) と
  0.3 dB 以内、40 本で最大 3.5 dB、20 本では**低次の部分音まで 1–4 dB 動く**。
  打ち切りは高域を消すだけでなく、接触のチャタリングを介して低次にも波及する。
  **演奏経路では絞らない。** 48 kHz のこの区間は全数 61–75 本で、`MAX_MODES = 256`
  に対して余裕がある。
- **参照**: `segment.rs` の `Segment::new` / `Decimation`、`render --string --os` で再測できる

## [D-011] 撥の剛性は物理定数ではなく接触時間からの校正値

- **発生フェーズ**: Phase 1
- **分類**: 仕様上の制約
- **状態**: **恒久**
- **内容**: `HammerParams::wood()` の `stiffness = 1e8` は、**剛体壁への接触時間が
  木の撥の実機レンジ (0.1–0.3 ms) に入るように掃引で決めた**。木材のヤング率から
  導いた値ではない。ヘルツ接触の等価剛性は接触面の曲率に強く依存し、撥の先端の
  丸みの実測が無い以上、独立には決められない。
- **校正の根拠** (剛体壁、v = 2 m/s、os = 64):

  | K | 接触時間 | ピーク力 |
  |---|---|---|
  | 1e12 (当初) | 0.005 ms | 6913 N ← 明らかに非物理 |
  | 1e9 | 0.084 ms | 435 N |
  | **1e8 (採用)** | **0.212 ms** | **173 N** |
  | 1e7 | 0.533 ms | 69 N |

  採用値はピーク力が弦の張力 (130 N) と同オーダーに収まる点も妥当。
  レザー 3e8 (0.67 ms)、フェルトは PhyPiano の実測校正値 4.5e9 (0.95 ms) を維持。
- **面の順序はテストで固定**: 木 < レザー < フェルト (接触時間)。
- **参照**: `hammer.rs` の `HammerParams`、`render --contact-table --stiffness` で再測できる

## [D-012] 木の撥はチャタリングし、接触時間は収束した観測量ではない

- **発生フェーズ**: Phase 1
- **分類**: モデル
- **状態**: **対応済み** (再接触を許す形に変更)
- **症状**: PhyPiano から移植した状態機械は**最初の離脱で Released に落として
  二度と触れさせない**。木の撥でこれを使うと接触が 23 µs で終わり、撥がまだ弦へ
  2 m/s で向かっているのに力を出せなくなる。倍率を変えると低次の部分音が 10 倍
  動く (os=4 と os=16 で 51.8 vs 4.4) という形で発覚した。
- **原因**: フェルト (接触 1–4 ms) は 1 回の接触で運動量を渡しきるので
  最初の離脱 = 打撃の終わりでよかった。木の撥は弦のほうが軽くて速く「逃げる」ため、
  1 回の接触では運動量のごく一部しか渡らない。実機の撥は弦の戻りに叩き返されるまで
  **複数回触れる** (チャタリング)。
- **対応**:
  1. 離脱時に撥がまだ弦へ向かっている (`velocity > 0`) なら `Approaching` に戻し、
     再接触を許す。弦から遠ざかる向きで離れたときだけ `Released`
  2. 活動窓が閉じる保証が無くなるので、`MAX_ACTIVE_SEC = 20 ms` で打ち切る
     (オーバーサンプルのコストを有界にする)。実測では遠端からの反射 (約 3 ms) が
     撥を跳ね返すので、通常この上限には達しない
- **帰結**: **「接触時間の合計」は木の撥では収束した観測量ではない** (倍率を上げる
  ほど微細な接触を数えて増える)。弦上の接触の検証は、フェルト面 (1 回で閉じる) の
  単調性と、木は「0.2–2 ms のオーダーに収まり、最終的に離れる」ことだけを固定した。
  剛体壁での接触時間 (こちらは収束する) は 0.1–1.0 ms・単調減少をテストで固定。
- **参照**: `hammer.rs` の `step` / `MAX_ACTIVE_SEC`、`segment.rs` のテスト

## [D-013] 出力の校正は暫定。ブリッジ力は打撃スパイクが支配的

- **発生フェーズ**: Phase 2
- **分類**: 音質 / 仕様上の制約
- **状態**: **Phase 5 (響板) で再校正する**
- **内容**: 楽器の出力はブリッジ力の和 [N] で、**打撃過渡のスパイクが支配的**。
  実測 (treble-short 相当、打弦点 0.09):

  | 撥の速度 | 生ピーク [N] | 持続部の部分音振幅 |
  |---|---|---|
  | 0.5 m/s | 4.7 | — |
  | 2.0 m/s | 21.5 | 約 1.5 |
  | 6.0 m/s | 83.3 | 約 2 |

  **クレストファクタが 20–40 倍**ある。ピークは速度に対してほぼ線形だが、
  持続部よりはるかに速く伸びる (高次ほど強い `∝ n` のブリッジ重みを、短い接触が
  フルに叩くため)。
- **暫定対応**: `CALIBRATED_GAIN = 0.004` (ff 単音のピーク ≈ −9 dBFS)。
  そのぶん持続部は小さめに出る。
- **なぜ今直さないか**: このスパイクは実機では響板 (高域が落ちる伝達) と
  ブリッジのインピーダンスが濾す成分で、Phase 5 で響板が入るとクレスト
  ファクタごと変わる。今ここで整形すると Phase 5 の校正と二重になる。
- **測定上の教訓**: **打撃直後の窓と持続部の窓でピークを比べないこと。**
  同じ音でも桁が違う。`note_off_does_not_stop_the_ring` テストはこれで一度
  誤判定した (打撃過渡を含む窓 vs 含まない窓の比較になっていた)。
- **参照**: `phydulcimer-plugin/src/lib.rs` の `CALIBRATED_GAIN`

## [D-017] 全音階配置なので楽器に無い半音は鳴らない。トレブル左は +2 cent

- **発生フェーズ**: Phase 3
- **分類**: 仕様上の制約
- **状態**: **恒久** (実機の性質の再現)
- **内容**: 2 つの「バグに見える仕様」をここに固定する。

  **(a) 未マップの MIDI 鍵は無音。** 15/14 は全音階配置 (G/D メジャー) で、
  G#・Bb・D#・F などの半音は楽器に存在しない。鳴る音高は 44 位置で 27 種類。
  例外は D メジャーの導音 C# (C#5 / C#6 がトレブル左にある)。
  クロマチックな MIDI データを流すと**当該ノートだけ無音になるのが正しい**。
  埋めるための仮想弦は作らない (楽器でなくなる)。必要なら将来オプションで。

  **(b) トレブル左側は 12 平均律より +2 cent 高い。** ブリッジが弦長をちょうど
  2:3 に分けるので、左は右の**純正5度上 (702 cent)**。平均律の 700 cent との
  差がそのまま乗る。同じ音高がトレブル右にもある音では右 (平均律) が優先される
  ので、実際に +2 cent で鳴るのは**左にしか無い音** (C#5, A5, B5, C#6, D6)。
  実機の調律師は左右の妥協点にブリッジを動かす — それを再現する「ブリッジ位置」
  パラメータは Phase 7。
- **配置の出典について**: 15/14 の音の並びは製作者により差がある。採ったのは
  Dusty Strings 系の標準的な 5 度間隔チューニングの**代表値**。表駆動なので
  差し替えられる。
- **参照**: `layout.rs`、`scaling.rs` の純正5度の導出、`render --table`

## [D-015] パラメータの反映がブロック内のイベントに追い越されていた

- **発生フェーズ**: Phase 2
- **分類**: 不具合
- **状態**: **修正済み**
- **症状**: ABI テストで「Strike Position を変えて叩いてもノッチが動かない」
  「Level を変えても音量が同じ」。パラメータ変更と打鍵を**同じブロック**に
  入れると、打鍵が古い値を使っていた。
- **原因**: ゲインと打弦点を `process` の**ブロック先頭で 1 回だけ**読んでいた。
  CLAP のイベントはブロック内にサンプル精度で並ぶので、後から来た
  `ParamValueEvent` は次のブロックまで反映されない。DAW ではパラメータ変更と
  打鍵が同じブロックに乗ることは普通にある。
- **対応**: ゲインはイベントバッチを処理した**後**に読む。打弦点は
  `ParamValueEvent` を受けた場で楽器へ同期する (ただの store で、係数の再構築は
  次の打撃まで起きない)。
- **教訓**: ブロック単位のパラメータ読みは「ブロックの先頭」ではなく
  「イベント処理の後」。PhyPiano は毎バッチ `apply_params` を呼ぶ構造だった
  ので、この罠を踏んでいなかった。
- **参照**: `phydulcimer-plugin/src/lib.rs` の `process` / `handle_event`、
  ABI テスト `strike_position_parameter_moves_the_notch` が回帰を固定

## [D-016] 鳴っている弦への再打弦が発散していた (ループ再生で LUFS +66)

- **発生フェーズ**: Phase 2 (**ユーザーの DAW 実機確認で発見**)
- **分類**: 不具合
- **状態**: **修正済み**
- **症状**: egui-clap-host のループ再生で、周回のたびに音が大きくなり
  **LUFS +66 まで上昇**した。当初はホスト側の問題も疑われたが、こちらの
  物理のバグだった。再現テスト (ff で 0.1 秒おきに 30 連打) では
  **非有限値まで発散**した。
- **原因**: 撥が毎回**位置 0 (弦の静止位置) から出発**していた。鳴っている弦は
  打弦点が変位している (強打後で ±数 mm)。弦が撥側に変位している瞬間に叩くと、
  **出発の瞬間に有限の圧縮 `Δ = 0 − y_s` が生じ、`K·Δ^1.5` で数千 N の
  非物理的スパイク**が出る。音が大きいほど変位が大きく、変位が大きいほど
  スパイクが大きいので、ループ再生の再打弦が**正帰還**になる。

  変位 2 mm なら `1e8 × (2e-3)^1.5 ≈ 8900 N` — 通常の打撃のピーク力
  (数百 N) の 1 桁以上上。
- **なぜ自動テストで出なかったか**: 単発の打弦は静止した弦 (変位 0) から
  始まるので、この経路を通らない。`a_second_strike_adds_to_the_ringing_string`
  は連打しても「有限であること」しか見ていなかった。**発散は繰り返しの中で
  しか育たない** — 2 打では音量差として見えても、しきい値を割らない。
- **対応**: [`Hammer::strike_at`] を新設し、撥を**弦の現在変位から出発**させる。
  接触は圧縮 0 (弦の表面) から始まり、力は連続に立ち上がる。ダンパーの無い
  楽器では再打弦が常態なので、これは修正というより**この楽器に必須の物理**。
- **回帰テスト**:
  - core: `repeated_ff_strikes_converge_to_a_bounded_roll` — 30 連打で
    「単発の 50 倍未満」「20 打目 → 30 打目で 1.5 倍未満」に収束
  - ABI: `looped_restrikes_do_not_diverge` — ループ再現 (0.21 秒 × 40 打)
- **教訓**: **「有限である」のテストは発散の初期を素通しする。** 繰り返しの
  ある系は「増え続けていないこと」を定常に達した 2 点の比で固定すること。
- **参照**: `hammer.rs` の `strike_at`、`segment.rs` の `strike`

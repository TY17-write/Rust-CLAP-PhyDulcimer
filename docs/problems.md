# 既知の問題・制約

本プロジェクトの問題を1箇所に集約する。**問題を見つけたらその場で追記する** (後回しにしない)。

リアルタイム制約ゆえに**意図的に諦めた近似**も「仕様上の制約」として記録する。
これが設計判断の記録になり、後から「なぜこうなっているのか」を追える。
**やらなかった判断こそ記録に値する。**

## 記入書式

```markdown
## [D-000] 一行で分かる表題
- 発生フェーズ: Phase N
- 分類: 音質 / 性能 / 検証手法 / 移植性 / 仕様上の制約 / 未解決
- 状態: 未対応 / 回避策あり / 恒久 / 修正済み (コミットへのリンク)
- 症状: 観測される事実
- 原因: 分かっていれば。**分からなければ「未特定」と書く**
- 回避策 / 対応方針:
- 参照: 論文・コミット・計画の該当節
```

## [D-001] 部分音の T60 は 0.4 秒より短いと測れない

- **発生フェーズ**: Phase 0
- **分類**: 検証手法
- **状態**: **未対応** (Phase 1 で必要になったら直す)
- **症状**: `analyze --partial-t60` が短い減衰に対して `—` を返す。単一の減衰正弦波
  (1000 Hz) で T60 を振って測った境界:

  | 設計 T60 | 測定 | R² |
  |---|---|---|
  | 1.000 s | **1.000** | 1.0000 |
  | 0.600 s | **0.600** | 1.0000 |
  | 0.500 s | **0.500** | 1.0000 |
  | 0.375 s | — | — |
  | 0.250 s | — | — |

  **0.5 秒までは正確、0.375 秒から測れない。**
- **原因**: [`estimate_partial_t60`] は窓 200 ms / ホップ 50 ms が固定で、
  `fit_t60` は「ピークから −5 dB 落ちた点」から「−20 dB 落ちた点」までに直線を
  当てる。この 15 dB ぶんの時間は `T60/4` なので、T60 = 0.375 s なら 0.094 s =
  ホップ 2 個ぶんしかなく、`end <= start + 2` の条件で棄却される。
- **対応方針**: 窓とホップを引数にする。目安は **ホップ ≤ T60/12**。
  ただし適切な値は「測りたい T60 の範囲」で決まり、それは Phase 1 で弦の減衰を
  設計してから確定する。**先に決め打ちしない。**
- **なぜ Phase 0 で直さないか**: この楽器は減衰が長い (ダンパーが無い) ので基音側は
  問題にならない。困るのは高次部分音と高音のコースで、そこは Phase 1 で
  実際の値が出てから合わせるほうが確実。
- **危険**: **Phase 1 で必ず当たる。** 高音側の弦は T60 が 0.5 秒を切る見込みで、
  そのとき「減衰が測れない」ではなく「減衰が無い」と誤読しないこと。
- **参照**: `tools/analyze/src/lib.rs` の `estimate_partial_t60` / `fit_t60`

## [D-002] 部分音が混在すると測れる T60 の下限が上がる

- **発生フェーズ**: Phase 0
- **分類**: 検証手法
- **状態**: **原因未特定**
- **症状**: 8 本の部分音を重ねた信号 (f0 = 220 Hz、`--t60 3.0 --t60-taper 1.0`、
  第 n 部分音の設計 T60 = 3.0/n) を測ると、n = 5 / 7 / 8 だけ `—` になる。

  | n | 設計 T60 | 測定 |
  |---|---|---|
  | 1 | 3.000 | **3.000** |
  | 2 | 1.500 | **1.500** |
  | 3 | 1.000 | **1.000** |
  | 4 | 0.750 | **0.750** |
  | 5 | 0.600 | — |
  | 6 | 0.500 | **0.500** |
  | 7 | 0.429 | — |
  | 8 | 0.375 | — |

  n = 7 / 8 は [D-001](#d-001-部分音の-t60-は-04-秒より短いと測れない) で説明が付く。
  **説明が付かないのは n = 5 (0.600 s) が落ちて n = 6 (0.500 s) が通ること。**
  単独の正弦波なら 0.600 s も 0.500 s も測れている (D-001 の表)。
- **原因**: 未特定。仮説は 2 つあるがどちらも確かめていない。
  1. 隣接部分音の裾が窓 200 ms の Goertzel に漏れ込み、減衰の途中で床を作る
  2. `find_partial` が返した実測周波数 (1105.18 Hz、設計 1105.40 Hz) のずれで
     測定点が部分音の肩に乗り、包絡が単調でなくなる
- **対応方針**: D-001 でホップを可変にするときに再現するかを見る。点が増えれば
  どちらの仮説でも改善する見込み。**それでも残るなら仮説 2 を潰す** (走査の刻みを
  細かくして周波数を追い込む)。
- **教訓**: **測定器が「測れない」と言ったとき、それを「値が無い」と読まないこと。**
  Phase 1 以降、減衰設計を検証するのはこの関数なので、沈黙の意味を取り違えると
  モデル側を無駄に触ることになる。
- **参照**: `tools/analyze/src/lib.rs`

## [D-003] WAV の書き出しが render と analyze の 2 か所にある

- **発生フェーズ**: Phase 0
- **分類**: 仕様上の制約
- **状態**: **恒久** (意図的)
- **症状**: `tools/render/src/main.rs` の `write_wav` と、`phydulcimer_analyze` の
  `write_wav` が同じことをしている (約 30 行)。
- **なぜそうしたか**: 共有すると **レンダラが解析ツールに依存する**という筋の悪い
  依存方向になる。逆に WAV I/O だけの crate を切ると、Phase 0 の時点で crate が
  1 つ増える。**30 行の重複のほうが安い。**
- **食い違ったときにどう気づくか**: `analyze` が `render` の出力を読めなくなるので、
  Phase 0 の完了条件 (`render` → `analyze` で設計値が読める) がそのまま検出器になる。
  加えて `tools/analyze/tests/roundtrip.rs` が lib 側の往復を固定している。
- **見直す条件**: プラグイン側 (Phase 2) でも WAV を書くようになったら、3 か所目に
  なる前に crate を切る。

## [D-004] --peak の既定を PhyPiano から変えた

- **発生フェーズ**: Phase 0
- **分類**: 仕様上の制約
- **状態**: **恒久** (意図的)
- **内容**: `render --peak` の既定を **0 (正規化しない)** にした。PhyPiano は 0.9。
- **理由**: PhyPiano では A/B 比較のたびに `--peak 0` を付け忘れ、**2 本のレベルが
  揃って差が消える**事故を繰り返した (引き継ぎメモに「頻出事故」として残っている)。
  既定を安全側に倒すほうが、注意力に頼るより確実。
- **副作用**: 出力が小さいまま書かれるので、そのまま聴くと音が小さい。聴くときは
  明示的に `--peak 0.9` を付ける。
- **固定方法**: `tools/render/src/main.rs` の `peak_defaults_to_no_normalisation`
  テストが 0 を固定している。**変えるならこのテストごと変えることになる。**

## [D-005] 信号全体の T60 はこの楽器では意味を持たない

- **発生フェーズ**: Phase 0
- **分類**: 検証手法
- **状態**: **恒久**
- **内容**: `analyze --t60` は信号全体の RMS 包絡に単一の指数を当てる。
  打弦楽器では部分音ごとに減衰時間が違うので、全体の包絡は
  「前半は高次部分音の速い減衰、後半は基音の遅い減衰」の 2 段になり、
  単一の指数では表せない。
- **ダルシマーではさらに悪い**: **ダンパーが無いので他の弦が共鳴して鳴り続ける。**
  1 音を鳴らしても、全体の包絡はその弦の減衰を表さない。
- **使ってよい範囲**: Phase 0 の疎通確認 (単一の減衰正弦波) まで。
  モデルが入ったら `--partial-t60` に切り替える。
- **参照**: `plan.html` の P10 (音色の追い込み)

## [D-006] 参照音源を持たない

- **発生フェーズ**: Phase 0 (計画時の決定)
- **分類**: 仕様上の制約
- **状態**: **恒久** (ユーザー確認済み、2026-08-31)
- **内容**: 実機の録音を用意しない。Pianoteq KIViR の Cimbalom は別の楽器
  (ダンパー付き・4 本弦) なので絶対比較には使わない。
- **影響**: PhyPiano が音質の追い込みで使った主要な梃子 (`--compare` による
  「参照より何 dB」) が丸ごと無い。
- **代わりに何を基準にするか**: **物理量が文献値の範囲に入ること**が唯一の外部基準。
  線径・張力・接触時間・インハーモニシティ B を Phase 1 / Phase 3 の完了条件に
  置いてある。**ここを緩めると寄る辺が無くなる。**
- **参照**: `plan.html` §10、`research.md` §5

## [D-007] モデル本体がまだ無い

- **発生フェーズ**: Phase 0
- **分類**: 未解決
- **状態**: **Phase 1 で解消**
- **内容**: `phydulcimer-core` にあるのは疎通確認用の減衰正弦波 (`smoke`) だけ。
  弦・ハンマー・ブリッジ結合・響板・箱・ROOM はすべて未実装。
- **この状態で何が保証されているか**: `render` → WAV → `analyze` の経路が
  設計値どおりの数値を返すこと。**測定器が信用できる状態**を先に作った。
- **参照**: `plan.html` §07 の実装フェーズ
